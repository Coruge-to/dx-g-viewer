# dxg-viewer ガイド

最終更新: 2026-11-22

自分の精密採点DX-Gの履歴を見るための、個人用のアプリです。公式のDAM★とものAPIから採点を集めて、Streamlitで表示します。非公式サイト（dx-g.clubdam.info）に頼らずに、自分のデータだけを見ることが目的です。

このドキュメントは、2つのことを書きます。

1. カラオケ店で歌った採点が、自動で、画面に出るまでの仕組み（厚めに書きます）
2. 画面側の機能と、開発のメモ

---

## 1. 全体像

```
カラオケ店でDAM★ともにログインして歌う
        │  （採点結果が、DAMのサーバーに記録される）
        ▼
公式API  GetScoringDxgListXML.do          ← 日本国内のIPからだけ届く
        │  5分おきに、PCが、新しい採点があるかを問い合わせる
        ▼
scripts/update.py   新しい採点IDだけ取得して、dataset/history.jsonl に追記
        ▼
scripts/sync.py     dataset/ の変化だけを commit し、GitHub へ push（開発のコミットは push しない）
        ▲
Windows タスクスケジューラ「dxg-sync」が、5分おきに sync.py を起動
        ▼
app.py（Streamlit）  ページを開くたびに history.jsonl を読んで表示
        ▼
同じLANのPC・スマホから  http://<このPCのIP>:8501/  で見る
```

PCが起きていて、ログインしている間だけ、動きます。

## 3. カラオケ店から画面までの流れ（自動更新の仕組み）

### 3.1 歌ってから、画面に出るまで

1. カラオケ店で、DAM★ともにログインして、精密採点DX-Gで歌います。
2. 採点の結果が、DAMのサーバーに記録されます。
3. 家のPCが、5分おきに、公式APIへ「新しい採点はあるか」を聞きます。
4. 新しい採点があれば、1件ずつ詳しく取得して、保管庫に追記します。
5. 保管庫が変わったら、commitして、GitHubへpushします。
6. 画面を開き直すと、一番上に、新しい採点が出ます。

**サーバーに採点が出るまでの遅れは、まだ測っていません。**次のカラオケで測ります（7章）。

### 3.2 公式API

- アドレス: `https://www.clubdam.com/app/damtomo/scoring/GetScoringDxgListXML.do`
- 認証は、カード番号（`cdmCardNo`）だけです。`cdmToken` は、送っても確認されないので、使いません。
- 日本国内のIPからだけ、つながります。海外のIPやクラウドの実行環境からは届きません。そのため、自動更新は、GitHub Actionsではなく、自宅のPCで動かしています。
- 文字コードは、Shift_JISを指定しています（`enc=sjis`）。
- 返ってくるのはXMLです。`result/statusCode` が `0000` なら成功です。

呼び出しは2種類あります。

| 用途 | 主なパラメーター | 返るもの |
|---|---|---|
| 一覧 | `pageNo`, `detailFlg=0`, `dxgType=1`, `UTCserial` | 1ページに5件。採点ID（`scoringDxgId`）と日時。`hasNext` が次のページの有無 |
| 詳細 | `scoringDxgId`, `detailFlg=1` | その1件の全項目（レーダー、区間のグラフ、ビブラートなど） |

一覧は、新しいほうから、最大200件までです。

### 3.3 update.py の動き

1. カード番号を、環境変数 `DAM_CARD` か、リポジトリ直下の `.env` から読みます。無ければ、終了コード2で止まります。
2. 保管庫の、既知の採点IDを、すべて読み込みます。
3. 一覧を、1ページ目から順に読みます。
   - 保管庫に無いIDを、新しいIDとして集めます。
   - **既知のIDに当たったら、そこで止めます。**それより古いものは、取得済みだからです。
   - 次のページに進むときは、2秒待ちます。最大40ページ・200件までです。
4. 新しいIDが無ければ、一覧の1回だけで終わります。普段は、これです。
5. 新しいIDがあれば、1件ずつ、詳細を取得します。サーバーの負荷を抑えるため、**1件ごとに6〜10秒（ランダム）待ちます。**5曲なら約1分です。
6. 取得した詳細を、保管庫の形式に変換して、追記します。失敗した1件は、飛ばして、次へ進みます。
7. 新しい順に並べ直して、`history.jsonl` を書き直し、`meta.json` を更新します。
8. 最後に `done: added N / M` と出力します。終了コードは、全部取れれば0、一部が失敗なら1です。

失敗して飛ばしたIDは、保管庫に入らないので、**次の実行で、また、新しいIDとして、取り直されます。**

通信は、1回失敗しても、5秒、10秒、15秒と、間を空けて、最大3回まで、やり直します。

`--dry-run`（一覧を見るだけ。書き込まない）と、`--heartbeat`（`checked_at` を更新する。過去の、GitHub Actions用）の、2つのオプションがあります。

### 3.4 保管庫に入れる形（dxg_lib.py）

公式のXMLを、以前の非公式サイトが持っていたJSONと、同じ形に変換します。

- 公式の数値を、表示用の値にします。点数は1000で割る。ビブラートの種類は、番号からラベル（A-1、C-2、ひし形など）にする。声域は、音名（hiEなど）にする。
- 非公式サイトが計算していた項目（`p_int`、`sta_10`、`int_10`、ビブラートの種類の名前など）は、同じ決まりで計算し直します。
- 分析レポートのコメントは、`comment_master.json` から、番号で引きます。
- **公開しない項目は、ここで外します。**カード番号、端末のシリアル、決済ID、管理用の項目です（`PUBLIC_DROP`）。

### 3.5 sync.py の動き

定期実行の入口です。

1. ロックファイル（`logs/.sync.lock`）で、二重起動を防ぎます。1時間以上たった古いロックは、無視します。
2. `update.py` を動かします。終了コード2（カード番号が無い）は、ログに書いて終わります。
3. `dataset/` に変化があれば、`git add dataset` して、`dataset` だけをcommitします（ステージ済みの他のファイルは、巻き込みません）。メッセージは「data: 新規N件を追加」です。
4. **GitHubより先にあるコミットのうち、「先頭から続く、`dataset/` だけを変えたコミット」までを、pushします。**
   - 判定は、メッセージではなく、コミットが変えたファイルで行います。
   - 手元の開発のコミット（`site/` や `app.py` など）は、pushしません。その上に乗ったデータのコミットも、開発のコミットがpushされるまで、保留します（失われません）。
   - 保留があると、ログに、`保留: ...` と書きます（状態が変わったときだけ）。
   - 失敗したら、`git pull --rebase --autostash` してから、もう1回pushします。それでも失敗したら、ログに残して、次の実行に任せます。
5. 結果を、`logs/sync.log` に書きます。512KBを超えたら、古いログに回します。

ログに出る行は、次のとおりです。

| ログ | 意味 |
|---|---|
| `update: 新規 N 件を追加` | 新しい採点が入った |
| `commit: data: 新規N件を追加` | commitした |
| `push: N コミットを反映` | データのコミットを、pushした |
| `保留: 手元の開発コミットなど N 件は、...` | 開発のコミット（と、その上のデータのコミット）を、pushしていない。確認してから、手でpushする |
| `ERROR: DAM_CARD が未設定` | `.env` を確認する |
| `update.py exit=1: ...` | 一部の詳細が取れなかった（次回に取り直す） |
| `ERROR commit` / `ERROR push` | gitの失敗。内容が、続けて書かれる |

### 3.6 タスクスケジューラ（dxg-sync）

| 項目 | 値 |
|---|---|
| タスク名 | `dxg-sync` |
| 実行するもの | `pythonw.exe scripts\sync.py`（画面を出さない）。作業フォルダは、リポジトリ。`sync.py` が呼ぶ `git` も、`CREATE_NO_WINDOW` を付けて呼ぶので、黒い窓が出ない（下の注意） |
| 間隔 | **5分おき**（2026-11-25に、10分から変更。`task.ps1` の既定は10分なので、登録し直すときは、`-Minutes 5` を付ける）。登録の少し後から、期限なしで繰り返す |
| 取りこぼし | 開始時刻に動けなかったとき（PCが寝ていたときなど）は、動けるようになってすぐ、実行する |
| 二重起動 | しない（新しいほうを捨てる） |
| 最大の実行時間 | 30分 |
| バッテリー | バッテリー駆動でも動く |
| 実行するユーザー | ログインしているユーザーだけ（ログオフ中は動かない） |

**注意（2026-11-25）: 黒い窓が一瞬出る件**: タスクは `pythonw.exe`（窓なし）で動くが、そこから `git.exe`（コンソールのプログラム）を呼ぶと、**呼ぶたびに**、黒い窓が一瞬出る（1回の実行で、`git` を5〜10回呼ぶので、数回、点滅する）。`sync.py` の `run()` で、`subprocess.run(..., creationflags=CREATE_NO_WINDOW)` を指定して、窓を作らないようにした（`git` が呼ぶ子のプロセスも、同じ隠れたコンソールを使うので、出ない）。`git` を8回呼ぶ試験で、窓の数は、指定なしが8個、指定ありが0個。新しく `subprocess` で外部のプログラムを呼ぶときも、同じ指定を付ける。

操作は、`scripts\task.ps1` で行います。何度実行しても、同じ結果になります。

```powershell
.\scripts\task.ps1                # 10分おきで登録（既定。いまは、-Minutes 5 で、5分おきに登録している）
.\scripts\task.ps1 -Minutes 5     # 5分おきに変更（再登録で上書き）
.\scripts\task.ps1 -Status        # 登録状況、前回と次回の実行、ログの末尾
.\scripts\task.ps1 -Remove        # 登録を削除
```

公式APIへの負荷を考えて、1分未満の間隔は受け付けません。5分以上を勧めます。

### 3.7 画面が、新しいデータを読む仕組み

- `app.py` は、ページを開くたびに `dataset/history.jsonl` を読みます。読み込みは、ファイルの更新時刻をキーにして、覚えています。**ファイルが変われば、次のページ読み込みで、自動で、読み直します。Streamlitの再起動は、いりません。**
- 採点結果画面で使うデータは、`static/dxgdetail/<版>/history.jsonl` にコピーされます。版は、ファイルの更新時刻から決まるので、保管庫が変われば、次のページ読み込みで、新しい版が作られます。
- `history.jsonl` が無いときだけ、`backup/` の最新のCSVを読みます。

### 3.8 動いていることを確かめる

| 知りたいこと | コマンド |
|---|---|
| タスクが登録されて、動いているか | `.\scripts\task.ps1 -Status` |
| サーバーに、新しい採点が出ているか（書き込まない） | `python scripts\update.py --dry-run` |
| 今すぐ、更新して反映したい | `python scripts\sync.py` |
| 更新だけして、pushしたくない | `python scripts\sync.py --no-push` |
| 自動更新が作ったコミット | `git log --grep='^data:'` |
| 最新の件数と日時 | `dataset/meta.json` を開く |

`--dry-run` の出力の読み方は、次のとおりです。

```
list page1: 5 items, newest=20260302175639   ← サーバーの最新の採点日時
known=1001 new=0                              ← 手元の件数と、新しい採点の数
```

`new` が1以上なら、サーバーには出ているのに、手元には、まだ入っていません。

### 3.9 うまく動かない場面

| 症状 | 原因の候補 | 見るもの |
|---|---|---|
| ずっと更新されない | PCがオフ、スリープ、ログオフ中 | `task.ps1 -Status` の「前回」の時刻 |
| 前回の結果が0以外 | スクリプトの失敗 | `logs/sync.log` |
| `statusCode` が `0000` でない | サーバー側の障害やメンテナンス | `update.py --dry-run` の出力。時間をおいて再実行 |
| 通信エラーが続く | 日本国外のIP、VPN、回線 | VPNを切る。ブラウザで公式サイトを開けるか |
| `ERROR push` | GitHubの認証が切れた、ネットワーク | `git push` を手で実行して、エラーを見る |
| `DAM_CARD が未設定` | `.env` が無い、または空 | `.env` を確認する |
| 同じ行が2回出る | 起きないはず（採点IDで重複を防ぐ） | `history.jsonl` の `scoringDxgId` |
| 一部の曲だけ入らない | 詳細の取得に失敗（次回に取り直す） | `update.py exit=1` のログ |

### 3.10 注意

- **コードのコミットは、自動ではpushされません。**`sync.py` がpushするのは、`dataset/` だけを変えたコミットです（2026-11-22に直しました。以前は、手元の未pushのコミットを、すべてpushしていたので、コードをcommitすると、10分以内に、GitHubへ出ていました）。コードのコミットは、確認してから、手で `git push` します。
- 開発のコミットが、未pushのまま残っているあいだ、新しいデータのコミットも、保留されます（失われません）。手で `git push` したあとの、次の実行で、送られます。その間も、画面には、新しい採点が出ます（画面は、手元のファイルを読むため）。
- カード番号は、`.env` にだけ置きます。`.env` は、Git管理外です。保管庫には、カード番号を入れません。
- リポジトリは公開です。`dataset/` に入れる項目は、公開してよいものだけです（3.4）。
- 一覧の上限は200件です。1回の実行の間に、200件を超えて歌うことは、ないはずです。
- 1曲ごとに6〜10秒待つので、更新に時間がかかるのは、正常です。

## 6. 画面側のメモ

### 6.1 画面の種類

| 画面 | 場所 | 内容 |
|---|---|---|
| 歌唱履歴 | `?mode=history` | すべての歌唱。新しい順。日付や曲名のリンクで絞り込み |
| 曲別最高点 | `?mode=best` | 曲ごとの最高点。日付の右に、過去に歌った回数（同じ曲名・歌手名の件数。回数でも並べ替えられる）。歌唱履歴の表には、回数の列は無い |
| その他集計 | `?mode=others` | 最高点別の曲数（棒グラフ）と、ビブラートタイプの割合（円グラフ。直近200曲） |

PC版は、幅1000px以上で、1300px以上では、拡大して表示します。幅1000px未満が、スマホ版です。

### 6.2 ページ送り

- 50件ずつです。アドレスの `page=N` で指定します。
- 数字は、最大5つの窓です（例: 全部で21ページなら、1〜3ページ目は「1 2 3 4 5」、4ページ目は「2 3 4 5 6」）。
- 一番下までスクロールすると、ページ送りの下端で止まります（下の余白は0）。ページが1つしかないときは、細い余白が付きます。

### 6.3 画像の保存

表（そのページ分）、グラフ、採点結果画面は、右クリックまたは長押しで、画像として保存できます。

- 画面のすぐ上に、保存用のPNG画像を、透明度1%で重ねています（`blob:` 形式）。
- 表は、`site/tablesave.js` が、画面の表を、SVGのforeignObjectで画像にします。余白は、上下左右16pxです。下端は、実際に描かれた表から、測って決めます。
- スマホ（指で触る端末）では、画像を、最初から、ずっと、押される状態にして、普通のタップは、下の要素へ渡します。iPhoneは、触れた瞬間に、長押しの対象を決めるためです。
- パソコンでは、右ボタンを押した瞬間に、切り替えます。

**Chrome（iPhone）では、保存できません。**約10〜20%より低い透明度の画像を、長押しの対象から外すためです。20%にすると、表とレーダーチャートが、透けて見えるので、1%のままにしました。Chromeでも保存したくなったら、保存ボタンを置く方式にします。BraveやSafariでは、保存できます。

試験用に、画像の長い辺の上限を変えるには、アドレスの末尾に `&tsmax=8192` を付けます。実機の状況を見るには、`&tsdebug=1` を付けます。

### 9.6 キャッシュ（更新が届かないとき）

GitHub Pages は、すべてのファイルを、10分間キャッシュします（`Cache-Control: max-age=600`）。F5（通常の再読み込み）で、確認し直されるのは `index.html` だけで、しかも、アドレスごとに、別々にキャッシュされます（`/` と `?mode=best` は、別）。何もしないと、JS・CSSを更新しても、最大10分、画面ごとに、古い版が残ります（2026-11-22に、実際に起きました）。

対策として、次の仕組みにしています。

1. 公開のとき、`version.json`（`{"v":"<commitの識別子>"}`）を作る。
2. `index.html` は、更新しない固定の殻で、`version.json` を、毎回、確認し直して（`cache: "no-cache"`）、`viewer.js?v=<版>` を読み込む。
3. `viewer.js` は、自分に付いた版を、`detail.js`、`tablesave.js`、`charts.js`、`detail.css` のアドレスにも付ける。`detail.js` の中の `import`（`assets.js`、`vib_gif.js`）には、公開のとき、ソースの `__VER__` を、同じ版に置き換えて付ける。

アドレスに版が付くので、新しいデプロイの後は、次のページ読み込みで、新しい版が読まれます（`index.html` が古いままでも）。`version.json` は、ごく小さなファイルで、確認し直しは、軽い通信だけです。データ（`history.jsonl`）は、読み込みのたびに、更新を確認する作りです。

ローカルや、Streamlit版の試験（`tools/copy_static_for_test.ps1`）では、`version.json` が無いので、版なしで読みます（そのままで動きます）。

それでも、古い版が見えるときは、`Ctrl+F5`（または `Ctrl+Shift+R`）で、キャッシュを無視して、読み込み直します。

### 9.7 採点結果画面のビブラートの波形

右下の緑の枠の波形は、`site/detail.js` の `cleanWave()` が、規則で作ります（Streamlit版も、同じ `detail.js` を使うので、同じ形です）。もとは、非公式サイトの波形GIFをなぞった線（`vib_gif.js`）でしたが、折れや不ぞろいがあって、波に見えなかったので、作り直しました。

**規則**: 波形は「中心線 + 振幅 × 正弦波」です。座標は、GIFの座標（幅89・高さ37・中心18.5）。8タイプのGIFに当てはめて、誤差0.2〜0.5pxで合う規則を見つけました。

| タイプ | 波の形 |
|---|---|
| A-1〜C-3 | 文字（A/B/C）が周期で、数字（1/2/3）が振幅。枠の中に、A は6.5周、B は4.5周、C は3.5周。振幅は 5.4 / 10.8 / 16.4。A-3 は、元の画像が無いが、同じ規則で作れる |
| N | 直線（中心） |
| D・E | 中心線が、上昇（D）または下降（E）。振幅は8.2。周期は B と同じ |
| F | 最初の山と谷まで振幅16.4で、そのあと8.2まで、直線で縮む |
| G | F を、左右に反転（180度回転）した形。8.2から16.4へ広がる |
| H | ひし形。振幅が 5.4 → 16.4（真ん中の山と谷）→ 5.4。上下対称 |

**決まり（見た目を変えるときは、守る）**

- 左端は谷（画面の下）から始まり、右端は山で終わる。波の数が、半周期の奇数倍（6.5・4.5・3.5周）なので、枠の中心で180度回しても、同じ形になる（点対称）。D・E・H・N も、同じ。F と G は、互いを180度回した形。
- 振幅の上限は16.4。枠の内側（縦1.2〜30.8）に、線（太さ2.2）が触れない限界で、中心18.5から、上下に16.46。元のGIFの実測は16.9まであったが、枠に触れるので、全体を16.4/16.9に縮めた（比率は、そのまま）。小さい側の8.2は、16.4の半分。H の端の5.4は、A-1の振幅。
- 左右は、枠にぴったりくっつける（波は、枠の内側の角丸の形で切り抜く）。上下は、枠に触れない。
- 種類の文字（H など）は、他のラベルと同じ縁取り文字（Arial 太字14・背景色 `#222` の縁取り）。以前の半透明の長方形は、N の直線の右端が暗くなる段差ができたので、やめた。

波形を変えたいときは、`cleanWave()` の定数（`WAVE_ABC`、`WAVE_X0/X1`、各タイプの式）を直します。`vib_gif.js` は、知らない種類が来たときの代わりとして、残してあります。

### 9.8 採点結果画面の、文字の寄せ方（`site/detail.js`）

#### ♭（音域の `m2A♭～hiD♭`）

書体の ♭ は、全角の幅（15px）で、前後に隙間ができて浮き、背も大文字より高い（約12.6px。大文字は約10.8px）。そこで、端末が選んだ書体の ♭ を、そのまま使いながら、次のように揃えます（`inkBox()`、`flatMetrics()`、`textWithFlats()`）。

1. **字の範囲を、ピクセルから測る。** 字を100pxで、canvas（200×200）に描き、色のついた画素（アルファ64超）の、左右・上下の端を探す。`measureText` の `actualBoundingBox` は使わない（iPhone の Safari 系では、左右が `left=0 right=100`、つまり、送り幅いっぱいで返り、余白を削れなかった。2026-11-22に、実機で確認）。
2. **左右の余白を削る。** 前後に、`FLAT_GAP`（1.0px。15pxの文字のとき）だけ、空ける。
3. **高さを、大文字（E）の上端とベースラインに、揃える。**
4. **太らせる。** 書体の ♭ は細い（Windowsで、棒が `I` の0.21倍。iPhone は、さらに細い）ので、棒の太さを、大文字 `I` の棒の何倍かにそろえ、足りない分だけ、縁取り（`stroke`）で太らせる。`I` の棒に対する比は、**スマホ（画面幅1000px未満）が0.5、PCが0.35**（`FLAT_STEM_NARROW`、`FLAT_STEM_WIDE`）。PCは、0.5だと太すぎた。固定の太らせ量だと、書体が細い iPhone で、細すぎた。
5. **太らせた分の高さを、補正する。** 縁取りの半分が、上下にふくらむので、縁取りを含めた外側が、大文字の高さに合うよう、♭ の大きさと位置を直す（`fs = (size × cap − w) / (asc + desc)`。`w` と `fs` は、4回の繰り返しで決める）。

測れなかったとき（NaN など）は、Windows（Yu Gothic）での実測値を使います（`asc 0.8 / desc 0.04 / l 0.4 / r 0.71 / cap 0.72 / stem 0.0346 / stemI 0.1446`）。

自前の図形の ♭ も、試しましたが、浮いて見えたので、やめました（書体の字を測って揃える形のほうが、自然でした）。

#### キーの ＋ と －

保管庫には、全角の ＋ ・ － が入っています（`dxg_lib.py` の `key_text`。10件）。表示のときだけ、半角の `+` と `−`（U+2212。`+` と同じ幅の、本物のマイナス）にします（`keyText()`）。保管庫のデータは、変えていません。並べ替えの変換（`table_data.py`）は、全角にも半角にも対応しています。

#### ボーナス点を、小数第3位まで

公式のデータは、文字列で、末尾の0が省略されます（`"1.1"`、`"1.89"`、`"98.07"`、`"93"`）。ボーナス点では、103件が該当します。表示は、`fix3()` で、小数第3位まで、そろえます（素点・右のグラフの吹き出しも、同じ関数）。点数の大きな数字（`97.292` など）は、もともと、`padEnd` で、0を補っています。

#### ラベルと値の間の余白

黄色い小さなラベルと、白い値が、隙間なしだと、「計6.1」「プボックス」「ー±0」のように、くっついて見えました。余白は、2種類です。

| 余白 | 使う場所 | 決め方 |
|---|---|---|
| `labelGap()`（5px） | `音程` ⇔ `正確率`、`合計` ⇔ `秒数`、`タイプ` ⇔ `型`、`キー` ⇔ `値` | 下段の左の項目（安定性の「まっすぐ」）の右端と、左の青線の右端の余白 m（-1px。ほぼ無い）を、`タイプ ボックス型`（タイプの値で最長の5文字。`ノンビブ形` も同じ）の「型」の右端と、右の青線の右端の余白に、等しくする。そのときの「プ」と「ボ」の間の余白 |
| `statGap()`（約1.8px） | 正確率 ⇔ 数値 ⇔ `%`、表現力・抑揚・しゃくり・こぶし・フォールの、ラベル ⇔ 数値 ⇔ 単位（点・回） | 一番右の項目 `フォール N回`（Nは1桁。x=358から）の「回」の右端が、グラフの右端（x=425。`11 + 420 - 6`）に、ちょうど合う間隔 |

`フォール` は、2桁（10回など）のときだけ、グラフの右端（425）に合わせて、左へずらします。こぶしと、ぶつかる記録は、データには、ありません。

データ全体で確かめたこと: 音域の行（`キー`・値まで）は、最大でも右端が428.6で、青線の右端（440）を越えない。`合計` の行は、最大でも右端が320.8で、波形の枠（338）に届かない。

座標（青線の10〜216・225〜440、「まっすぐ」の173、「タイプ」の338、グラフの右端）は、コードの中の値から、計算します。位置を変えるときは、`labelGap()` と `statGap()` の定数も、見直します。

### 9.9 スマホの表の点数（`site/viewer.js`・`viewer.css`）

- **大きさ**: 12px。字間は、**標準**（以前は、全部で-0.7px詰めていて、横に潰れて見えた）。
- **7桁（`100.000`）だけ**、字間を-0.7px詰める。点数の文字数が6を超えたとき、`viewer.js` が `score-100` という目印を付け、`viewer.css` が詰める。通常は6桁（`98.927`）で、7桁は、満点だけ。大きさは、すべての点数で同じにする（7桁だけ小さくすると、見栄えが悪い）。手元のデータには、100.000の記録が無い。
- **幅**: 点数の列は、画面幅の14%（390pxで約47.6px、375pxで約45.6px）。`100.000` が、12px・-0.7pxで、約38pxなので、収まる。幅375px（最も狭い iPhone）でも、はみ出さない。
- **見た目の中央揃え**: `text-align: center` は、字の送り幅で中央に置くので、先頭の字の左の空きと、末尾の字の右の空きの差だけ、描かれる数字が、左右にずれる（iPhone で、約0.35px左に寄って見えた。末尾が `1` の行は、約0.8px左）。各字（0〜9と`.`）の左右の空きを、100pxで描いて、ピクセルから測り（`glyphInset()`）、その差を、左右の余白（`padding-left` か `padding-right`）として足す（`centerPad()`）。
- **6桁の点数は、全行で、同じ余白（「.」の位置をそろえる）。** Arial の数字は、どれも同じ幅なので、6桁の点数は、箱の位置が同じで、「.」の位置が、全行でそろう（Streamlit時代も、そうだった。専用の処理は無く、中央揃えと、数字の幅が同じことによる）。`centerPad()` を、行ごとに足すと、末尾が `1` の行が1.6px動くなど、「.」の位置が、行ごとにずれて、数値によって、描かれる位置が違って見えた（2026-11-23に、実機で指摘）。そこで、6桁は、全データの `centerPad()` の平均（`scorePad6()`）を、全行に足す。6桁でない点数（7桁の `100.000` など）は、「.」の位置が、そもそも違うので、行ごとに、`centerPad()` で、字の空きから寄せる。
- **カーニングを切る（`font-kerning: none`）。** Arial には、`11`（1が続く並び）を詰める指定があり、12pxで0.9px・14pxで約1px詰まる。`11` を含む値だけ、箱が狭くなり、「.」の位置がずれる。「`1` が絡むと、横の幅が狭くなる」という、実機での指摘の原因。他の並び（`17`・`71`・`1.`・`7.` など）は、詰まらない。
  - **点数（中央揃え）**: `11` を含む点数（14件）は、箱が狭く（スマホ12pxで35.78px。通常は36.68px）、中央揃えで、「.」が0.46px右へずれた。PC版（14px）も、同じ（41.79px。通常は42.83px。0.52px）。
  - **右寄せの枠（素点・ボーナス点などの `.num-slot`）**: 「.」より後ろに `11` があると（素点23件・ボーナス点21件）、「.」の位置が、右端から約0.9pxずれる。
  - **切る場所**: `viewer.css` の `.num-slot`・`.score-cell-pc`・`.score-cell`（PC版・スマホ版とも）。切ると、6桁の点数の箱の幅と「.」の位置が、全行で、そろう（スマホ49行・PC49行で確認。右寄せの枠も、`11` を含む値で、同じ距離）。
- **目の錯覚の補正**: ピクセルでは、ぴったり中央でも、`98.927` は、点（.）の前が2桁・後が3桁で、iPhone で、まだ左に寄って見えた（この一部は、上の、行ごとの余白と、`11` のカーニングで、位置がずれていたためと、後で分かった。2026-11-23）。そこで、さらに、右へ、`SCORE_OPTICAL_SHIFT`（0.3px。中心の移動量）だけ寄せる。iPhone の実機で、0 / 0.1 / 0.2 / 0.3 / 0.4 を並べて比べ、0.3 に決めた（最初に比べた0.4〜1.6は、多すぎた）。余白 p で、中心が p/2 動くので、足す余白は、その2倍（0.6px）。
  - **2026-11-23の注意（試験中）**: 本番では、`SCORE_OPTICAL_SHIFT` を、一時的に **0（補正なし）** にして、様子を見ている（`e2f61d5`）。左に寄って見えて気になるときは、0.3に戻す（`site/viewer.js` の1行。コメントに、戻し方を書いてある）。
- **`100.000` にも、補正が掛かる（行ごとの `centerPad()`）。** さらに、7桁の字間（-0.7px）の分も、戻す。字間は、末尾の字の後ろにも付くので、箱が0.7px短くなり、描かれる数字が、箱の中心より、0.35px右へずれる。`centerPad()` の結果に、`SCORE_100_LS`（-0.7。`viewer.css` の `.score-100` と、同じ値）を足して、左へ戻す。先頭の `1` は、左の空きが大きい（約1.3px）ので、これも、`centerPad()` が、補正する。補正後は、`100.000` も、他の行も、描かれる数字のずれが、目の錯覚の補正の分（`SCORE_OPTICAL_SHIFT`）に、そろう（0.1pxのとき、+0.08〜0.09pxで確認）。
- **縁取りで太らせる案**（`-webkit-text-stroke`）は、全体に違和感があったので、見送り。数字の列（素点・チ計など）は、11pxのまま。12pxが、列幅の限界（素点の列と、ビ秒・ビ回・ビタの列が、12pxで、余りが0.2〜0.5px）で、13px以上は、列の幅の配分を変える必要がある。

### 9.11 採点結果画面の、点数の推移グラフの縦軸（`site/detail.js` の `songGeom()`）

縦軸の下端（`yMin`）と、目盛りの刻み（`yStep`）は、曲ごとに、次の順で決める。上端は、いつも100。

**ひとことで言うと**: 下端は、「いちばん低い点が、横軸の線に引っかからない（間隔が6以上ある）最も高い目盛り」にする。引っかかるなら、ひとつ下の目盛りにする。（例: 最低33点なら、30が横軸。31点なら、30では間隔が約2で引っかかるので、20が横軸。）刻みは、5点おき（混むときだけ10点おき）。

1. **下端の最初の値**: いちばん低い点（全系列・全回）と、下の線（横軸）の間隔が、`Y_BOTTOM_GAP`（6。画像の座標で、点の印の半径は4〜5）以上になる値。ただし、94より上にはしない・0より下にもしない。以前は、最低点の1点下で、最低点が低い曲では、◆が横軸の線に、くっついた。
2. **刻みは、5点おき。間隔が狭いときだけ、10点おき。** 5点おきの目盛りの間隔(`ph × 5 ÷ 範囲`)が、`Y_LABEL_MIN_GAP`（18。文字の高さ13より少し広い）より狭いときだけ、10点おきにする。10点おきが上限（最低点が3点のような極端な曲でも、スマホ版の間隔は約16で、文字が重ならない）。`ph` は、グラフの描画の高さ（PC版 約231・スマホ版 約162）。そのため、間引かれ始める最低点は、PC版が約36点以下、スマホ版が約55点以下。
3. **下端を、目盛りの位置にそろえる**（刻みの倍数まで、下げる）。いちばん下の目盛りの線が、横軸に近すぎると（くっつく・二重に見える）、見栄えが悪いので、横軸の線と、いちばん下の目盛りの線を、重ねる（ラベルが、横軸の線の高さに来る）。下端が94（上限）のときは、そろえない（いちばん下の目盛りの95が、横軸から離れているため）。下端が変わると、範囲が変わって、刻みが変わることがあるので、数回、繰り返す。
4. **線も、ラベルと同じ本数にする**（間引いた目盛りにだけ、線を引く）。

例（スマホ版）: 夜空のクレヨン（最低33点）は、30〜100の10点おき。◆（33点）は、横軸の30の線の約3px上で、線に触れない。チルドレンレコード（45点）は、40〜100。君とプログレス（90点台）は、90〜100の5点おき。マトリョシカ（5点）は、0〜100の10点おき。

- **経緯（2026-11-24）**: 極端な推移の曲（夜空のクレヨン）で、5点おきの目盛りが、スマホ版で多すぎた（14本・間隔約11.6で、文字が重なった）。非公式サイトは、Highcharts 4.0.1 の自動の目盛り（約72pxに1本。刻みは1・2・2.5・5・10の倍数。下端は、最低点の少し下）だが、高い点数（80〜100点）では、5点おきが細かすぎないので、「5点おきを基本に、混むときだけ間引く」ルールにした（ユーザーの判断）。◆が、横軸や目盛りの線に、くっつく・重なる件も、同時に直した。
- **確かめ方**: `static/pagestest/ytick_diag.html`（6曲の、左右比較）と `ycrop.html`（下端の拡大）。どちらも Git管理外。動きの途中の絵（開く動き）は、最後の画像と、大きさが違うので、確認ページでは、`openDetail(..., { animate: false })` で、動きなしで開く。

### 9.12 採点結果画面の、PC用とスマホ用の切り替え（`site/detail.js`）

- **境目は 1000px**（1000px以上がPC用）。表の切り替え（`viewer.css` の `@media` の 1000px）と、同じ。以前は900pxで、900〜999pxでは、表はスマホ版なのに、この画面はPC用になっていた（2026-11-26にそろえた）。境目を変えるときは、両方を直す。
- **開いている間に幅が変わったら、作り直す**（端末の回転・窓の大きさの変更など）。以前は、開いた瞬間の幅のまま、変わらなかった。`resize` のあと150ms待って、PC用/スマホ用か、表示の倍率が変わるときだけ、作り直す。開く動きは出さず、前の画面を残したまま、新しい画面と差し替える（一瞬消えないように）。高さだけの変化（スマホのアドレスバーの出し入れ）と、指で拡大して見ている間は、作り直さない。
