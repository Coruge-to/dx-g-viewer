# dxg-viewer ガイド

最終更新: 2026-11-22

自分の精密採点DX-Gの履歴を見るための、個人用のアプリです。公式のDAM★とものAPIから採点を集めて、Streamlitで表示します。非公式サイト（dx-g.clubdam.info）に頼らずに、自分のデータだけを見ることが目的です。

このドキュメントは、2つのことを書きます。

1. カラオケ店で歌った採点が、自動で、画面に出るまでの仕組み（厚めに書きます）
2. 画面側の機能と、開発のメモ

---

## 1. 全体像

```
カラオケ店でDAM★ともにログインして歌う
        │  （採点結果が、DAMのサーバーに記録される）
        ▼
公式API  GetScoringDxgListXML.do          ← 日本国内のIPからだけ届く
        │  10分おきに、PCが、新しい採点があるかを問い合わせる
        ▼
scripts/update.py   新しい採点IDだけ取得して、dataset/history.jsonl に追記
        ▼
scripts/sync.py     dataset/ の変化だけを commit し、GitHub へ push（開発のコミットは push しない）
        ▲
Windows タスクスケジューラ「dxg-sync」が、10分おきに sync.py を起動
        ▼
app.py（Streamlit）  ページを開くたびに history.jsonl を読んで表示
        ▼
同じLANのPC・スマホから  http://<このPCのIP>:8501/  で見る
```

PCが起きていて、ログインしている間だけ、動きます。

## 3. カラオケ店から画面までの流れ（自動更新の仕組み）

### 3.1 歌ってから、画面に出るまで

1. カラオケ店で、DAM★ともにログインして、精密採点DX-Gで歌います。
2. 採点の結果が、DAMのサーバーに記録されます。
3. 家のPCが、10分おきに、公式APIへ「新しい採点はあるか」を聞きます。
4. 新しい採点があれば、1件ずつ詳しく取得して、保管庫に追記します。
5. 保管庫が変わったら、commitして、GitHubへpushします。
6. 画面を開き直すと、一番上に、新しい採点が出ます。

**サーバーに採点が出るまでの遅れは、まだ測っていません。**次のカラオケで測ります（7章）。

### 3.2 公式API

- アドレス: `https://www.clubdam.com/app/damtomo/scoring/GetScoringDxgListXML.do`
- 認証は、カード番号（`cdmCardNo`）だけです。`cdmToken` は、送っても確認されないので、使いません。
- 日本国内のIPからだけ、つながります。海外のIPやクラウドの実行環境からは届きません。そのため、自動更新は、GitHub Actionsではなく、自宅のPCで動かしています。
- 文字コードは、Shift_JISを指定しています（`enc=sjis`）。
- 返ってくるのはXMLです。`result/statusCode` が `0000` なら成功です。

呼び出しは2種類あります。

| 用途 | 主なパラメーター | 返るもの |
|---|---|---|
| 一覧 | `pageNo`, `detailFlg=0`, `dxgType=1`, `UTCserial` | 1ページに5件。採点ID（`scoringDxgId`）と日時。`hasNext` が次のページの有無 |
| 詳細 | `scoringDxgId`, `detailFlg=1` | その1件の全項目（レーダー、区間のグラフ、ビブラートなど） |

一覧は、新しいほうから、最大200件までです。

### 3.3 update.py の動き

1. カード番号を、環境変数 `DAM_CARD` か、リポジトリ直下の `.env` から読みます。無ければ、終了コード2で止まります。
2. 保管庫の、既知の採点IDを、すべて読み込みます。
3. 一覧を、1ページ目から順に読みます。
   - 保管庫に無いIDを、新しいIDとして集めます。
   - **既知のIDに当たったら、そこで止めます。**それより古いものは、取得済みだからです。
   - 次のページに進むときは、2秒待ちます。最大40ページ・200件までです。
4. 新しいIDが無ければ、一覧の1回だけで終わります。普段は、これです。
5. 新しいIDがあれば、1件ずつ、詳細を取得します。サーバーの負荷を抑えるため、**1件ごとに6〜10秒（ランダム）待ちます。**5曲なら約1分です。
6. 取得した詳細を、保管庫の形式に変換して、追記します。失敗した1件は、飛ばして、次へ進みます。
7. 新しい順に並べ直して、`history.jsonl` を書き直し、`meta.json` を更新します。
8. 最後に `done: added N / M` と出力します。終了コードは、全部取れれば0、一部が失敗なら1です。

失敗して飛ばしたIDは、保管庫に入らないので、**次の実行で、また、新しいIDとして、取り直されます。**

通信は、1回失敗しても、5秒、10秒、15秒と、間を空けて、最大3回まで、やり直します。

`--dry-run`（一覧を見るだけ。書き込まない）と、`--heartbeat`（`checked_at` を更新する。過去の、GitHub Actions用）の、2つのオプションがあります。

### 3.4 保管庫に入れる形（dxg_lib.py）

公式のXMLを、以前の非公式サイトが持っていたJSONと、同じ形に変換します。

- 公式の数値を、表示用の値にします。点数は1000で割る。ビブラートの種類は、番号からラベル（A-1、C-2、ひし形など）にする。声域は、音名（hiEなど）にする。
- 非公式サイトが計算していた項目（`p_int`、`sta_10`、`int_10`、ビブラートの種類の名前など）は、同じ決まりで計算し直します。
- 分析レポートのコメントは、`comment_master.json` から、番号で引きます。
- **公開しない項目は、ここで外します。**カード番号、端末のシリアル、決済ID、管理用の項目です（`PUBLIC_DROP`）。

### 3.5 sync.py の動き

定期実行の入口です。

1. ロックファイル（`logs/.sync.lock`）で、二重起動を防ぎます。1時間以上たった古いロックは、無視します。
2. `update.py` を動かします。終了コード2（カード番号が無い）は、ログに書いて終わります。
3. `dataset/` に変化があれば、`git add dataset` して、`dataset` だけをcommitします（ステージ済みの他のファイルは、巻き込みません）。メッセージは「data: 新規N件を追加」です。
4. **GitHubより先にあるコミットのうち、「先頭から続く、`dataset/` だけを変えたコミット」までを、pushします。**
   - 判定は、メッセージではなく、コミットが変えたファイルで行います。
   - 手元の開発のコミット（`site/` や `app.py` など）は、pushしません。その上に乗ったデータのコミットも、開発のコミットがpushされるまで、保留します（失われません）。
   - 保留があると、ログに、`保留: ...` と書きます（状態が変わったときだけ）。
   - 失敗したら、`git pull --rebase --autostash` してから、もう1回pushします。それでも失敗したら、ログに残して、次の実行に任せます。
5. 結果を、`logs/sync.log` に書きます。512KBを超えたら、古いログに回します。

ログに出る行は、次のとおりです。

| ログ | 意味 |
|---|---|
| `update: 新規 N 件を追加` | 新しい採点が入った |
| `commit: data: 新規N件を追加` | commitした |
| `push: N コミットを反映` | データのコミットを、pushした |
| `保留: 手元の開発コミットなど N 件は、...` | 開発のコミット（と、その上のデータのコミット）を、pushしていない。確認してから、手でpushする |
| `ERROR: DAM_CARD が未設定` | `.env` を確認する |
| `update.py exit=1: ...` | 一部の詳細が取れなかった（次回に取り直す） |
| `ERROR commit` / `ERROR push` | gitの失敗。内容が、続けて書かれる |

### 3.6 タスクスケジューラ（dxg-sync）

| 項目 | 値 |
|---|---|
| タスク名 | `dxg-sync` |
| 実行するもの | `pythonw.exe scripts\sync.py`（画面を出さない）。作業フォルダは、リポジトリ |
| 間隔 | 10分おき。登録の1分後から、期限なしで繰り返す |
| 取りこぼし | 開始時刻に動けなかったとき（PCが寝ていたときなど）は、動けるようになってすぐ、実行する |
| 二重起動 | しない（新しいほうを捨てる） |
| 最大の実行時間 | 30分 |
| バッテリー | バッテリー駆動でも動く |
| 実行するユーザー | ログインしているユーザーだけ（ログオフ中は動かない） |

操作は、`scripts\task.ps1` で行います。何度実行しても、同じ結果になります。

```powershell
.\scripts\task.ps1                # 10分おきで登録（既定）
.\scripts\task.ps1 -Minutes 5     # 5分おきに変更（再登録で上書き）
.\scripts\task.ps1 -Status        # 登録状況、前回と次回の実行、ログの末尾
.\scripts\task.ps1 -Remove        # 登録を削除
```

公式APIへの負荷を考えて、1分未満の間隔は受け付けません。5分以上を勧めます。

### 3.7 画面が、新しいデータを読む仕組み

- `app.py` は、ページを開くたびに `dataset/history.jsonl` を読みます。読み込みは、ファイルの更新時刻をキーにして、覚えています。**ファイルが変われば、次のページ読み込みで、自動で、読み直します。Streamlitの再起動は、いりません。**
- 採点結果画面で使うデータは、`static/dxgdetail/<版>/history.jsonl` にコピーされます。版は、ファイルの更新時刻から決まるので、保管庫が変われば、次のページ読み込みで、新しい版が作られます。
- `history.jsonl` が無いときだけ、`backup/` の最新のCSVを読みます。

### 3.8 動いていることを確かめる

| 知りたいこと | コマンド |
|---|---|
| タスクが登録されて、動いているか | `.\scripts\task.ps1 -Status` |
| サーバーに、新しい採点が出ているか（書き込まない） | `python scripts\update.py --dry-run` |
| 今すぐ、更新して反映したい | `python scripts\sync.py` |
| 更新だけして、pushしたくない | `python scripts\sync.py --no-push` |
| 自動更新が作ったコミット | `git log --grep='^data:'` |
| 最新の件数と日時 | `dataset/meta.json` を開く |

`--dry-run` の出力の読み方は、次のとおりです。

```
list page1: 5 items, newest=20260302175639   ← サーバーの最新の採点日時
known=1001 new=0                              ← 手元の件数と、新しい採点の数
```

`new` が1以上なら、サーバーには出ているのに、手元には、まだ入っていません。

### 3.9 うまく動かない場面

| 症状 | 原因の候補 | 見るもの |
|---|---|---|
| ずっと更新されない | PCがオフ、スリープ、ログオフ中 | `task.ps1 -Status` の「前回」の時刻 |
| 前回の結果が0以外 | スクリプトの失敗 | `logs/sync.log` |
| `statusCode` が `0000` でない | サーバー側の障害やメンテナンス | `update.py --dry-run` の出力。時間をおいて再実行 |
| 通信エラーが続く | 日本国外のIP、VPN、回線 | VPNを切る。ブラウザで公式サイトを開けるか |
| `ERROR push` | GitHubの認証が切れた、ネットワーク | `git push` を手で実行して、エラーを見る |
| `DAM_CARD が未設定` | `.env` が無い、または空 | `.env` を確認する |
| 同じ行が2回出る | 起きないはず（採点IDで重複を防ぐ） | `history.jsonl` の `scoringDxgId` |
| 一部の曲だけ入らない | 詳細の取得に失敗（次回に取り直す） | `update.py exit=1` のログ |

### 3.10 注意

- **コードのコミットは、自動ではpushされません。**`sync.py` がpushするのは、`dataset/` だけを変えたコミットです（2026-11-22に直しました。以前は、手元の未pushのコミットを、すべてpushしていたので、コードをcommitすると、10分以内に、GitHubへ出ていました）。コードのコミットは、確認してから、手で `git push` します。
- 開発のコミットが、未pushのまま残っているあいだ、新しいデータのコミットも、保留されます（失われません）。手で `git push` したあとの、次の実行で、送られます。その間も、画面には、新しい採点が出ます（画面は、手元のファイルを読むため）。
- カード番号は、`.env` にだけ置きます。`.env` は、Git管理外です。保管庫には、カード番号を入れません。
- リポジトリは公開です。`dataset/` に入れる項目は、公開してよいものだけです（3.4）。
- 一覧の上限は200件です。1回の実行の間に、200件を超えて歌うことは、ないはずです。
- 1曲ごとに6〜10秒待つので、更新に時間がかかるのは、正常です。

## 6. 画面側のメモ

### 6.1 画面の種類

| 画面 | 場所 | 内容 |
|---|---|---|
| 歌唱履歴 | `?mode=history` | すべての歌唱。新しい順。日付や曲名のリンクで絞り込み |
| 曲別最高点 | `?mode=best` | 曲ごとの最高点。日付の右に、過去に歌った回数（同じ曲名・歌手名の件数。回数でも並べ替えられる）。歌唱履歴の表には、回数の列は無い |
| その他集計 | `?mode=others` | 最高点別の曲数（棒グラフ）と、ビブラートタイプの割合（円グラフ。直近200曲） |

PC版は、幅1000px以上で、1300px以上では、拡大して表示します。幅1000px未満が、スマホ版です。

### 6.2 ページ送り

- 50件ずつです。アドレスの `page=N` で指定します。
- 数字は、最大5つの窓です（例: 全部で21ページなら、1〜3ページ目は「1 2 3 4 5」、4ページ目は「2 3 4 5 6」）。
- 一番下までスクロールすると、ページ送りの下端で止まります（下の余白は0）。ページが1つしかないときは、細い余白が付きます。

### 6.3 画像の保存

表（そのページ分）、グラフ、採点結果画面は、右クリックまたは長押しで、画像として保存できます。

- 画面のすぐ上に、保存用のPNG画像を、透明度1%で重ねています（`blob:` 形式）。
- 表は、`site/tablesave.js` が、画面の表を、SVGのforeignObjectで画像にします。余白は、上下左右16pxです。下端は、実際に描かれた表から、測って決めます。
- スマホ（指で触る端末）では、画像を、最初から、ずっと、押される状態にして、普通のタップは、下の要素へ渡します。iPhoneは、触れた瞬間に、長押しの対象を決めるためです。
- パソコンでは、右ボタンを押した瞬間に、切り替えます。

**Chrome（iPhone）では、保存できません。**約10〜20%より低い透明度の画像を、長押しの対象から外すためです。20%にすると、表とレーダーチャートが、透けて見えるので、1%のままにしました。Chromeでも保存したくなったら、保存ボタンを置く方式にします。BraveやSafariでは、保存できます。

試験用に、画像の長い辺の上限を変えるには、アドレスの末尾に `&tsmax=8192` を付けます。実機の状況を見るには、`&tsdebug=1` を付けます。

## 7. 開発のメモ

### 7.1 起動

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py --server.port 8501 --server.headless true --server.address 0.0.0.0
```

- `scripts/` の中のモジュールは、Streamlitを起動したときに読み込まれます。**直したら、Streamlitを再起動します。**
- `site/` の中のファイルは、ページ読み込みのたびに、版つきのフォルダへコピーされます。再起動は、いりません。
- スマホからは、同じネットワークの `http://<PCのIP>:8501/` で見ます。

### 7.2 試験

## 9. 静的サイト（GitHub Pages）

PCを起動しておかなくても、スマホから見られるようにするための、移行です。公開アドレスは `https://coruge-to.github.io/dx-g-viewer/` です。

### 9.1 仕組み

```
dxg-sync（10分おき）が、新しい歌唱を取り込んで、dataset/ をcommit・push
        ▼
GitHub Actions（.github/workflows/pages.yml）が、site/ と dataset/ の3ファイルを集めて公開
        ▼
ブラウザが、index.html を開き、dataset/history.jsonl（gzipで約485KB）を読んで、画面を作る
```

- 公開するのは、`site/` の中身と、`dataset/` の3ファイル（`history.jsonl`、`meta.json`、`comment_master.json`）だけです。`app.py` や `scripts/` は、公開しません。
- 並べ替え・検索・絞り込み・ページ送りは、すべて、ブラウザの中で動きます。条件は、Streamlit版と同じ形のアドレス（`?mode=best&sort_col=...`）で決まります。
- 公開の範囲は、「Streamlitの表として見える範囲」です。データは、元から、公開リポジトリにあります。

### 9.1.1 画面のアドレス

| 画面 | 短い形 | 長い形 |
|---|---|---|
| 歌唱履歴 | `https://coruge-to.github.io/dx-g-viewer/`（条件なし） | `?mode=history` |
| 曲別最高点 | `…/dx-g-viewer/?best` | `?mode=best` |
| その他集計 | `…/dx-g-viewer/?stats` | `?mode=stats` |

- 画面の名前は、`history`・`best`・`stats` です。`stats` は、「その他集計」の名前です（もとは `others`）。
- 短い形は、他の条件と併用できます（例: `?best&page=2`、`?best&sort_col=sing_count&sort_dir=desc`）。
- 古い名前（`?others`、`?mode=others`、`?mode=statistics`）も、そのまま開きます（以前のブックマークや共有のアドレスのため）。
- 画面上のタブのリンクは、短い形（`./`、`?best`、`?stats`）です。並べ替え・ページ送り・検索で作られるアドレスには、`mode=` が入ります。
- Streamlit版のアドレスは、これまでどおり、`?mode=others` です（Streamlit版は、名前を変えていません）。

### 9.2 ファイル

| ファイル | 役割 |
|---|---|
| `site/viewer.js` | 表の画面。保管庫の1件を、表の1行にして（`toRow`）、PC版・スマホ版の表、ページ送り、ナビを作る。`app.py` の移植 |
| `site/charts.js` | その他集計のグラフ。`scripts/others_charts.py` と、`app.py` の `render_others` の移植 |
| `site/viewer.css` | 画面のCSS。先頭が、静的サイト用の土台（Streamlitが、もともと与えていた見た目）で、その下は、`app.py` の `DXG_CSS` と同じ |
| `site/fonts/` | Streamlitと同じ、Source Sans（SIL OFL） |
| `site/detail.js` ほか | 採点結果画面、表の画像保存。Streamlit版と同じファイルを、そのまま使う |

CSSは、`<style>` として差し込みます（表の画像保存 `tablesave.js` が、画面の `<style>` から、表の見た目を読み取るため）。

### 9.3 Streamlit版との違い

- 同じ順位（同点・同じタイプなど）の並びは、新しい順で安定します。Streamlit版（pandas）は、規則のない内部の並びでした。
- 検索は、大文字小文字を区別しない、文字の一致です。Streamlit版は、正規表現として扱っていました。
- 検索欄は、ページの中の入力欄です（Streamlit版は、別の小さなページ(iframe)の中でした）。iframeは、本体より少し遅れて読み込まれ、窓が一瞬遅れて出ていたためです。見た目は同じです。検索すると、ページ送りは、1ページ目に戻ります。
- ナビのタイトルの文字が、読み込み直後に縮んで見えるのを防ぐため、フォント（Source Sans）を先読みし、届いてから画面を描きます（最大1.5秒。届かなければ、待たずに描く）。
- 「その他集計」で、保存用の透明な画像が、右へはみ出して、横スクロールバーが出ていたのを、枠でクリップして直しました（Streamlit版には、まだ残っています）。

### 9.4 見た目が同じことの確かめ方

Streamlit版と静的版を、同じ幅のiframeで並べて、全要素の、位置・大きさ・CSSを突き合わせます。

1. `.\tools\copy_static_for_test.ps1` で、`static/pagestest/` へコピーする（Git管理外）。
2. Streamlit（8501）を動かして、`http://<PCのIP>:8501/app/static/pagestest/cmp.html?cases=[["mode=history",1280],["mode=best",390]]` を開く（`cases` は、[アドレスの条件, 幅] の一覧を、URLエンコードしたもの）。
3. 結果は、ページの `#out`（JSON）に出る。`ok: true` なら一致。

2026-11-22の確認結果: 歌唱履歴・曲別最高点・その他集計を、幅390・1000・1280・1500pxで、並べ替え・ページ送り・検索・絞り込みも含めて比べ、同順位の並びの違い以外は、すべて一致しました（約5000要素）。実機のiPhone（Safari・Brave）では、まだ確かめていません。

### 9.5 公開するとき

1. GitHubの設定（Settings → Pages → Source）を「GitHub Actions」にする（済）。
2. コミットをpushする。`site/` か `dataset/` が変わると、Actionsが、自動で、公開を更新する。
3. 確認: `https://github.com/Coruge-to/dx-g-viewer/actions` で成功を見て、公開アドレスを開く。

注意: 開発のコミット（`site/` など）は、`sync.py` が、自動では、pushしません（3.5）。手で `git push` します。

### 9.6 キャッシュ（更新が届かないとき）

GitHub Pages は、すべてのファイルを、10分間キャッシュします（`Cache-Control: max-age=600`）。F5（通常の再読み込み）で、確認し直されるのは `index.html` だけで、しかも、アドレスごとに、別々にキャッシュされます（`/` と `?mode=best` は、別）。何もしないと、JS・CSSを更新しても、最大10分、画面ごとに、古い版が残ります（2026-11-22に、実際に起きました）。

対策として、次の仕組みにしています。

1. 公開のとき、`version.json`（`{"v":"<commitの識別子>"}`）を作る。
2. `index.html` は、更新しない固定の殻で、`version.json` を、毎回、確認し直して（`cache: "no-cache"`）、`viewer.js?v=<版>` を読み込む。
3. `viewer.js` は、自分に付いた版を、`detail.js`、`tablesave.js`、`charts.js`、`detail.css` のアドレスにも付ける。`detail.js` の中の `import`（`assets.js`、`vib_gif.js`）には、公開のとき、ソースの `__VER__` を、同じ版に置き換えて付ける。

アドレスに版が付くので、新しいデプロイの後は、次のページ読み込みで、新しい版が読まれます（`index.html` が古いままでも）。`version.json` は、ごく小さなファイルで、確認し直しは、軽い通信だけです。データ（`history.jsonl`）は、読み込みのたびに、更新を確認する作りです。

ローカルや、Streamlit版の試験（`tools/copy_static_for_test.ps1`）では、`version.json` が無いので、版なしで読みます（そのままで動きます）。

それでも、古い版が見えるときは、`Ctrl+F5`（または `Ctrl+Shift+R`）で、キャッシュを無視して、読み込み直します。
